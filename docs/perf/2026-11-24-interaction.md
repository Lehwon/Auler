# 스크롤·끌기 중 CPU·프레임·메모리 (2026-11-24)

소프트웨어 렌더러는 유휴 메모리를 보고 골랐다. 실제 사용 중 비용도 확인하려고 200% 배율에서 스크롤과 끌기 중의 CPU, 프레임, 메모리를 쟀다.

## 방법

- 도구: `tools/measure-interaction.ps1`. 앱을 `AULER_BENCH=idle|scroll|drag`로 실행하면 3초 준비 후 앱이 Slint `dispatch_event`로 입력을 넣는다(실제 마우스는 움직이지 않음). CPU 시간(`GetProcessTimes`)과 Private Bytes(`GetProcessMemoryInfo`)는 앱이 직접 재고, 초당 렌더링 프레임은 `SLINT_DEBUG_PERFORMANCE=refresh_lazy,console`로 받는다.
- 시나리오
  - idle: 입력 없음(타이머만 60Hz로 돈다)
  - scroll: 기준자료 화면 500행 표를 16ms마다 휠 40px, 2초마다 방향 전환
  - drag: 시간표의 2교시짜리 카드를 누른 채 좌우 ±160px, 상하 ±70px로 흔들어 놓일 자리 표시가 계속 바뀌게 함
- 조건: [렌더러 측정](2026-11-24-slint-renderer.md)과 같은 PC, 2880×1800 @200%, 창 내용 1366×768(프레임 버퍼 2732×1536), 릴리스 빌드, 소프트웨어 렌더러
- 각 8초, 3회(scroll은 첫 줄 제외 수정 후 2회 재측정)

## 결과

| 시나리오 | CPU (코어 1개 기준) | 입력 중 FPS | Private 전 → 피크 → 후 (MB) |
|---|---|---|---|
| idle | 0.6~0.8% | 0 (다시 그리지 않음) | 21.1 → 21.2 → 21.2 |
| scroll | 31.5~34.8% | 61 | 21.5 → 21.7~21.8 → 21.5~21.8 |
| drag | 5.7~6.3% | 60~61 | 21.1 → 21.2 → 21.2 |

## 해석

- 두 상호작용 모두 60Hz 화면 주기를 유지했다. 목표로 둔 "클릭 피드백 100ms 이내"보다 여유가 크다.
- 메모리는 상호작용 중에도 0.5MB 안에서 움직였다. 소프트웨어 렌더러의 메모리 이점이 사용 중에도 유지된다.
- 비용 차이는 다시 그리는 면적에서 온다. 끌기는 놓일 자리 표시와 카드만 다시 그리고(부분 갱신), 표 스크롤은 표 영역 전체(200%에서 약 2300×1100 픽셀)를 매 프레임 다시 그린다.
- scroll의 코어 1개 34%는 16스레드 PC 전체로는 약 2%다. 배율 100%에서는 그릴 픽셀이 1/4이라 비용도 비슷하게 줄 것으로 보지만 재지 않았다.

## 남은 측정

- 100%, 125%, 150% 배율 (이 PC의 디스플레이 설정을 바꿔야 해서 사용자 확인 필요)
- 저사양 PC(4코어 이하)에서의 스크롤 CPU
- 장시간(30분 이상) 사용 후 메모리 증가
- 자동 편성·출력 중 피크 (M1·M3 구현 후)
